# 3s-mister-arm — MiSTer FPGA Port
### Based on [crowded-street/3sx](https://github.com/crowded-street/3sx) — a multiplatform port of *Street Fighter III: 3rd Strike* built from a PS2 decompilation

> **Note:** This project was formerly known as "3SX MiSTer." It has been renamed to **3s-mister-arm** to make clear that this is an **independent MiSTer port** — it is ***NOT*** an official release by the 3sx team. For support, please use this project's issue tracker — the 3sx team's Discord is not the right place for 3s-mister-arm questions.

A vibe-coded hybrid ARM + FPGA port of *Street Fighter III: 3rd Strike*
running on the [MiSTer FPGA](https://mister-devel.github.io/MkDocs_MiSTer/)
platform (DE10-Nano).

The game logic and software rendering run on the ARM Cortex-A9, while custom
FPGA modules handle video output timing, DDR3 framebuffer scanout, audio
buffering, and DAC conversion — the same native video path used by every
MiSTer FPGA core.

Based on a [decompilation](https://github.com/crowded-street/sfiii-decomp) of the
PlayStation 2 port. Requires a legally obtained copy of *Street Fighter III: 3rd
Strike* or *Street Fighter Anniversary Collection* for PS2 to play.

> **This is an experimental, fully vibe-coded MiSTer-focused fork of
> [crowded-street/3sx](https://github.com/crowded-street/3sx).**
> The entire MiSTer port layer — FPGA RTL, ARM code, wrapper, tooling, and
> docs — was generated by AI (Claude and Codex). See
> [AI Collaboration Disclosure](#ai-collaboration-disclosure) for full details.
> Expect rough edges, regressions, and breaking changes between revisions.

## How It Works

The MiSTer DE10-Nano is a Cyclone V SoC: a dual-core ARM Cortex-A9 at 800 MHz
bolted to an FPGA fabric. Most MiSTer cores are pure FPGA — the game logic,
rendering, and video output all happen in hardware. 3s-mister-arm takes a different
approach:

```
┌─────────────────────────────────────────────────────────────┐
│  ARM Cortex-A9 (Linux)                                      │
│                                                             │
│  Game logic ─► Software renderer ─► DDR3 framebuffer write  │
│  (CPS3 decomp)  (SDL3, 384x224)     (mmap @ 0x3A000000)    │
│                                                             │
│  ADX audio decode ─► ALSA ─► FPGA audio buffer              │
└──────────────────────────┬──────────────────────────────────┘
                           │ DDR3
┌──────────────────────────▼──────────────────────────────────┐
│  FPGA Fabric                                                │
│                                                             │
│  native_video_reader ─► dcfifo ─► video_timing_gen          │
│  (DDR3 burst read)      (line     (384x224 @ 59.6 Hz)      │
│                          buffer)       │                    │
│                                        ▼                    │
│                                   VGA_R/G/B/HS/VS/DE       │
│                                        │                    │
│                                   ┌────┴────┐               │
│                                   ▼         ▼               │
│                               yc_out    vga_out             │
│                             (S-Video)   (RGB/VGA)           │
│                                                             │
│  alsa.sv (audio FIFO + hurryup logic) ─► I2S DAC           │
└─────────────────────────────────────────────────────────────┘
```

The ARM does what CPUs are good at (game logic, complex rendering), the FPGA
does what FPGAs are good at (cycle-exact video timing, DAC output, audio
buffering). From the MiSTer framework's perspective this looks like any other
core generating its own video — the fact that the pixels came from the ARM is
invisible.

## Install

Extract a release ZIP onto the root of your MiSTer SD card. The archive is
FAT-rooted and places files at:

```
/media/fat/MiSTer_3S-ARM                     HPS wrapper executable
/media/fat/_Other/3S-ARM.rbf                  FPGA bitstream
/media/fat/games/3s-arm/
  ├── bin/3s-arm                              Game binary (ARM)
  ├── lib/                                 Shared libraries (SDL3, etc.)
  ├── resources/                           (empty — you supply the game data)
  └── scripts/                             Launch helpers
```

> **⚠️ FTP users:** If transferring files via FileZilla or another FTP client,
> set the transfer type to **Binary** (not Auto or ASCII). The default mode
> corrupts extensionless binaries like `MiSTer_3S-ARM` and `3s-arm`, causing the
> core to crash on launch.

After extracting, place your legally obtained game archive:

```
/media/fat/games/3s-arm/resources/SF33RD.AFS
```

Then add this section to `/media/fat/MiSTer.ini`:

```ini
[3S-ARM]
main=MiSTer_3S-ARM
```

## Running

1. Boot MiSTer normally.
2. Navigate to the **Other** core folder.
3. Launch **3S-ARM**.

If the core immediately exits back to MiSTer, the most common cause is a
missing `SF33RD.AFS`.

### CRT Troubleshooting

The native video path outputs at NTSC standard horizontal frequency
(15,734 Hz). Most 15 kHz CRTs and arcade monitors should sync directly
with `vga_scaler=0` (the default).

If you still cannot get a picture, try using the MiSTer scaler with a
custom video mode:

```ini
[3S-ARM]
main=MiSTer_3S-ARM
vga_scaler=1
video_mode=384,22,38,51,224,16,3,21,7788
```

This routes through the MiSTer scaler at 384x224 NTSC timing. Then open
the OSD (F12) and set **Aspect Ratio** to **Full** to avoid pillarboxing.
If your CRT expects composite sync, also add `composite_sync=1`. Note:
`vga_scaler=1` disables S-Video color output.

### OSD Options

Press F12 or the MiSTer menu button to open the OSD. All settings persist
across launches.

| Setting | Options | Effect |
|---------|---------|--------|
| **Game Mode** | Console / Arcade | **Console** (default) shows the normal title screen and menus. **Arcade** skips straight to the character select screen like a coin-op cabinet — no title screen, no mode select. This is a convenience setting for local play, not a gameplay accuracy toggle. |
| **Hold to Pause** | Off / On | When **On**, you must hold Start to pause instead of tapping it. Useful in Arcade mode to prevent accidental pauses during play. |
| **Button Check** | (trigger) | Opens an input verification screen showing real-time button presses for both players. Useful for tournament setups to confirm controller mappings. |
| **Aspect Ratio** | 4:3 / Full | Switches between 4:3 and Full. Only relevant when using the MiSTer VGA scaler (`vga_scaler=1`); has no effect on the native video path. |

### Performance

The game runs at 60 FPS during normal gameplay at stock 800 MHz. Frame
rate drops can occur in two main situations: **stages with complex
animated backgrounds** (e.g. Remy's and Chun-Li's stages), and **super art
activations**, which layer multiple translucent ghost sprites and
effects on top of the scene.

All performance settings are accessible from the **OSD menu** (press
F12 or the MiSTer menu button) and persist across launches.

#### Super Art Settings

These settings reduce rendering work during super art activations:

| Setting | Options | Effect |
|---------|---------|--------|
| **SA Activation** | Full / Cached BG | **Cached BG** snapshots the background once when a super art activates, skipping per-frame background re-rendering for the duration. Significant FPS improvement during supers on animated stages. |
| **SA Ghost Res** | Full / Half | **Half** renders ghost (after-image) sprites at half vertical resolution. Reduces ghost rendering cost by ~50%. |
| **SA Ghost Count** | 0–4 | Limits the maximum simultaneous ghost sprites per player. Default is 4 (vanilla). Reducing this directly reduces the number of translucent sprites composited per frame. |

For the best balance of visual fidelity and performance, try **Cached BG**
with ghost count at **3** or **4**. For maximum performance on demanding
scenes, combine **Cached BG** + **Half** ghost resolution + a lower ghost
count.

#### Overclock

The ARM CPU defaults to **stock 800 MHz**. Overclocking to 1000 or
1200 MHz can help maintain 60 FPS during heavy scenes.

You can cycle between 800 MHz (stock), 1000 MHz, and 1200 MHz from the
OSD menu. The new clock speed takes effect on the next game restart
(shown with a `*` in the OSD until applied). The setting persists across
launches.

**Note:** Not all DE10-Nano boards can run stably at 1200 MHz. If the
game crashes or freezes after overclocking, SSH into your MiSTer and
edit `/media/fat/games/3s-arm/config`. Find the `arm-clock` line and
change it back to stock:

```
arm-clock = 800
```

### Wrapper Core

The `MiSTer_3S-ARM` HPS executable acts as a bridge between the MiSTer menu
framework and the game. It:

- Loads the FPGA bitstream (`3S-ARM.rbf`)
- Initializes the native video path and audio
- Launches the game binary (`/media/fat/games/3s-arm/bin/3s-arm`) via `execve()`
- Manages the MiSTer OSD (on-screen display) overlay
- Handles signal cleanup and console switching

## FPGA Native Video Pipeline

The defining feature of this port is **FPGA-native video output** — the same
path every MiSTer core (Genesis, SNES, Neo Geo, etc.) uses for analog display.
This matters because:

- **Zero scaler latency.** The asynchronous MiSTer scaler (ascal) adds 1–2
  frames of buffering. The native path outputs pixels directly to the DAC as
  they're read from DDR3, with latency measured in scanlines, not frames.
- **CRT-correct timing.** The FPGA generates 15 kHz NTSC timing at 59.5993 Hz
  (matching the original CPS3 hardware) from a dedicated PLL. CRTs lock to
  this signal directly.
- **S-Video / composite / RGB.** The `yc_out` module encodes luma + chroma for
  S-Video and composite. RGB passes through directly. All analog outputs work
  without the scaler.

### Pixel Path

```
ARM renders 384x224 ARGB8888 (SDL3 software renderer)
  → Converts to RGB565 + writes to DDR3 @ 0x3A000000
    → native_video_reader.sv reads DDR3 in 96-beat bursts
      → Decodes RGB565 → RGB888, pushes into dcfifo line buffer
        → native_video_timing.sv outputs pixels at ce_pix rate
          → VGA_R/G/B/HS/VS/DE signals on clk_vid (~7.8 MHz pixel clock)
            → OSD composites on top (vga_osd, always in signal path)
              → yc_out (S-Video) or vga_out (RGB) → DAC → display
```

### DDR3 Memory Layout

```
0x3A000000 + 0x000   : Control word
                        [1:0]   active_buffer (0 or 1, double-buffered)
                        [31:2]  frame_counter (FPGA polls for new frames)
0x3A000000 + 0x100   : Buffer 0 (384 × 224 × 2 = 172,032 bytes, RGB565)
0x3A000000 + 0x2A200 : Buffer 1 (172,032 bytes, RGB565)
```

The ARM writes a complete frame to one buffer, then updates the control word.
The FPGA polls the control word and switches read address on the next vblank.
No SPI handshake needed per frame.

### Video Timing

| Parameter | Value |
|-----------|-------|
| Active pixels | 384 × 224 |
| H total | 495 |
| V total | 264 |
| Refresh rate | 59.5995 Hz |
| Pixel clock | 7.7885 MHz |
| H frequency | 15.734 kHz (NTSC standard, exact) |
| PLL config | Integer-N, dedicated video PLL: 50 MHz × 81/(5×26) = 31.1538 MHz (÷4 for pixel clock) |

HDMI output still works via the standard MiSTer scaler path (`video_mixer` →
ascal). CRT users get the direct analog path; HDMI users get the scaler. No
regression either way.

## Audio Pipeline

Audio uses the MiSTer FPGA's ALSA interface (`alsa.sv`). The ARM decodes ADX
audio and sends PCM samples via ALSA, which the FPGA buffers and outputs
through the I2S DAC.

Key tuning:
- FPGA hurryup thresholds tightened from ~170 ms → ~85 ms ramp-up
- ADX music buffer reduced from 400 ms → 100 ms
- SDL3 audio clock recovery prevents drift-induced delay buildup

## AI Collaboration Disclosure

**The entire MiSTer port is vibe coded.** Every commit on the `mister` branch
on top of upstream `main` was generated by AI — either
[Claude](https://claude.ai) (Anthropic, Opus model family) or
[Codex](https://openai.com/codex) (OpenAI). No human has reviewed the code

We believe in full transparency about this. If you're evaluating this code for

audited it. This README is also AI-generated and may or may not contain subtle
inaccuracies.

### What "Vibe Coded" Means Here

A human described what they wanted in natural language. An AI agent (Claude Code
or Codex) wrote the code, ran builds, and iterated on errors. In many cases the
AI agents also deployed to the MiSTer over SSH and verified results through
automated test runners. A persistent "ralph loop" process ran autonomously —
deploying builds to the MiSTer, capturing performance telemetry, and feeding
results back to the AI to guide optimization without human intervention.

### Scope

**Everything on the `mister` branch above upstream `main` is AI-generated.** This
includes:

- **FPGA SystemVerilog** — `native_video_reader.sv`, `native_video_timing.sv`,
  `native_video_top.sv`, PLL configuration, and all modifications to
  `menu.sv`. The FPGA modules that read pixel data from DDR3 and output
  native video to the DAC were designed and written entirely by AI, based on
  analysis of the [Groovy MiSTer](https://github.com/psakhis/Groovy_MiSTer)
  DDR3 reader and the MiSTer Avalon-MM interface.
- **FPGA audio tuning** — `alsa.sv` hurryup threshold changes, ADX buffer
  sizing.
- **ARM C code** — SDL3 renderer, framebuffer presenter, native video writer,
  ALSA audio output, ADX decode pipeline, OSD menu integration, frame pacing,
  clock recovery, and all MiSTer-specific platform code in `src/port/`.
- **HPS wrapper** — `thirdsarm_main.cpp`, `thirdsarm_wrapper.cpp`,
  `thirdsarm_core_context.cpp`, and all `Main_MiSTer` overlay modifications.
- **PLL design** — A dedicated integer-N video PLL producing 31.1538 MHz
  (50 MHz × 81/(5×26)), divided by 4 for a 7.7885 MHz pixel clock. This PLL
  is separate from the 100 MHz system PLL, which decouples video timing
  from system-clock constraints. H-freq is exactly the NTSC standard
  15,734 Hz, and V-freq matches CPS3's 59.59949 Hz to within 1.4 μHz.
- **S-Video / analog video** — Blanking distribution, YC encoding fixes, and
  the native video bypass that makes analog CRT output work without the
  scaler.
- **Build and deploy tooling** — `misterctl.sh`, `build-game.sh`,
  `build-core.sh`, `build-hps.sh`, cross-compilation pipeline, and deploy
  automation.
- **All documentation** — Every `docs/*.md` file on this branch (design docs,
  research notes, specs, plans, runbooks) was AI-generated.

### What the AI Did NOT Write

- **The game itself.** The PS2 decompilation (`src/sf33rd/`), character logic,
  move data, animation system, AcrSDK stubs, and the upstream software
  renderer are entirely human-written by Artem Pstygo, Evan K, and other contributors to
  [crowded-street/3sx](https://github.com/crowded-street/3sx).
  This is the bulk of the codebase.
- **The upstream MiSTer framework.** The `sys/` modules (ascal scaler,
  video_mixer, hps_io, DAC output) are community-maintained open source from
  [MiSTer-devel](https://github.com/MiSTer-devel).
- **The decompilation** that this project is built on.

## Building from Source

See [docs/building.md](docs/building.md) for full instructions. Quick overview:

### Game Binary (ARM cross-compile)

```bash
tools/mister/build-game.sh
```

Produces the ARM hard-float ELF at `build-mister/3s-arm`. Cross-compiles with
clang targeting `cortex-a9` with NEON.

### FPGA Bitstream (Quartus 17)

```bash
tools/mister-wrapper/build-core.sh
```

Produces `3S-ARM.rbf`. Requires Intel Quartus 17.0 (Cyclone V support).

### HPS Wrapper

```bash
tools/mister-wrapper/build-hps.sh
```

Produces `MiSTer_3S-ARM`.

### Release Package

```bash
tools/mister-wrapper/build-release.sh
```

Packages everything into a release ZIP ready for SD card extraction.
