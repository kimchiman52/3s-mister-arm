- Every cycle must begin with DEEP research before any code changes:
  - inspect the current living findings, active checklist, relevant local code paths, and existing gameplay telemetry/logs

  - if existing automated captures do not cover the user-observed transition/effect/stage-specific stalls, first add or recover the narrowest safe capture support needed to measure them

  - challenge whether the remaining ceiling is refresh/update, stage-specific game work, effect bursts, or measurement blind spots before editing runtime code
  - prefer new evidence over intuition when deciding whether the hardware is near a hard limit
- Only implement optimizations that are backed by that cycle's DEEP research. If the research does not support a safe/high-confidence change, record the result and move to the next candidate instead of forcing an implementation.
- Never leave the branch dirty between loops. If the repo is dirty at cycle start, do not block; instead treat the first part of that cycle as mandatory closure work:
  - inspect the dirty state
  - determine whether it is a verified keep, a diff that still needs MiSTer verification, or a failed experiment that can be safely rolled back
  - if MiSTer verification is still pending or the device gate is currently unhealthy, preserve that diff on a dedicated `preserve-*` branch with `tools/mister/preserve-blocked-work.sh` instead of rolling it back or pretending it was closed
  - return the current working branch to a clean committed state before moving on
- Exception: ignore any inherited dirty state in `tools/mister/package.sh`. Treat that file as user-owned/out-of-scope unless the user explicitly asks to change it; do not stage, commit, or revert it as part of a Ralph cycle.
- Before finalizing a cycle, run an independent code review agent pass on the diff, evaluate findings critically, apply only valid fixes, then rebuild/re-verify any runtime-changing diff.
- Every completed cycle must end on a clean git worktree with a real local commit.
- If a runtime-changing diff passes final verification, create the runtime commit for that loop.
- If research disproves every safe runtime change before implementation, or a runtime experiment is reverted after failing verification, fully roll back the runtime code, update the checklist/living findings, and create a docs-only closure commit for that loop.
- If a runtime-changing or measurement-support diff cannot be verified only because the MiSTer device gate is unhealthy, do not throw it away and do not create a fake docs-only closure for it. Preserve it on a `preserve-*` branch, record that it is pending verification, and make that preserved branch the next verification target once the device gate recovers.
- Measurement-support or scene-broadening code that is kept for future loops is not "research-only"; if it remains in the tree at cycle end, it must be committed in that cycle.
- Never leave a loop in a final `no-commit` state on the active branch. If verification is blocked by device health, preserve the diff on a dedicated branch with a real commit there, then return the active branch to a clean state.
- Never push to git remotes, never rebase, never rewrite history.
- Log what changed and why in concise commit messages.
- If a cycle inherits dirty state, resolve that state first instead of treating it as a blocker. Only use a stop note for truly exceptional cases where neither commit nor rollback can be completed safely.

Hard constraints (do not violate):
- Do not change gameplay behavior, game rules, move properties, collision/hit logic, input mapping semantics, simulation timing, RNG behavior, stage logic, menu flow, or resource content.
- Do not make changes that could alter determinism or game feel.
- Restrict code changes to performance-oriented implementation details (render/present path, buffering/copy costs, allocation patterns, logging overhead, I/O overhead, build/profile flags) without changing visible gameplay behavior.
- If a candidate optimization may affect gameplay behavior, skip it and choose a different optimization.
- If any applied change is suspected to affect gameplay behavior, revert that change immediately and continue with a safer approach.
- Objective is purely improved frame rate/stability on lower-powered MiSTer hardware.

End-of-cycle review gate (required):
- After implementing candidate optimizations, or before closing a docs-only rollback/research cycle, spawn a separate review agent/process to review the staged/working diff.
- Treat review findings as input, not absolute truth: validate each point against code and constraints before acting.
- Do not blindly apply every suggestion; reject findings that are incorrect, out-of-scope, or risk gameplay behavior.
- Apply only high-confidence, in-scope fixes.
- Re-run build and device verification after applying review-driven fixes to any runtime-changing diff.
- Commit only after the review gate passes and the cycle has returned to a clean final state.
